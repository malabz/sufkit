# sufkit 0.1.1 right-maximal query benchmark

> Terminology correction: this run was originally published as a MEM
> benchmark. The implementation guarantees right maximality but not left
> maximality, so the internal workload is now described as right-maximal exact
> matching. The numbers are unchanged; the interpretation is narrower.

This document records the original 0.1.1 release run. The 0.2.0 runner isolates
each internal method in a worker process and records
separate SA/ISA/LCP/CHILD/PWL phase times; see
[the 0.2.0 Sapling development report](0.2.0-sapling.md) for the updated
measurement path. The implementation baseline is
`e5c57364a5d0704e01eef178885c34eb5c159ce6`; later standard-profile work is
recorded at `04e3fc7666cedd37d3c437924d21ce623b436e02`.

The development harness now shares the four exact-benchmark profiles
(`smoke`, `quick`, `standard`, and `full`) and all six selectable scenarios.
Its controlled server matrix uses `mixed` for smoke, all six scenarios for
quick and standard, and `mixed`, `repeat-rich`, and `many-contig` for full.
Those future server rows are a different measurement protocol from the
historical numbers below and must not be pooled with them.

## Environment and commands

The release benchmark was run locally on 2026-08-23 under WSL2 Linux
5.15.167.4, using the configured GCC 13.3.0 compiler and CMake 3.28.3 on an AMD Ryzen 9 7940HX
(32 logical CPUs). Every indexed method used one build/query thread. The
MUMmer launcher reported version 4.0.1 and had SHA-256
`db2aa7dea6050147d9fb3a6c5a39c6a0733bccac2d580ac7c3a2fb9f12ff158e`
(the underlying `.libs/mummer` binary was
`74de4a544b5af897d843ce42b4c7a29f7c069c9d6756935b26b2a9f6dc9c17ca`).

The original executable used the former `mem` command/method names. The
following commands are the terminology-corrected equivalents for the current
CLI; no performance rerun was performed for the rename.

```bash
./build/release/sufkit bench \
  --workload right-maximal --profile smoke \
  --methods right-maximal-baseline,right-maximal-lcp,right-maximal-child,right-maximal-suffix-link,right-maximal-full,mummer4 \
  --min-lengths 20,50 \
  --mummer4 /path/to/mummer4/mummer \
  --output-dir build/bench/right-maximal-smoke

./build/release/sufkit bench \
  --workload right-maximal --profile quick --scenarios mixed,repeat-rich \
  --methods right-maximal-baseline,right-maximal-lcp,right-maximal-child,right-maximal-suffix-link,right-maximal-full,mummer4 \
  --min-lengths 20,50,100 \
  --mummer4 /path/to/mummer4/mummer \
  --output-dir build/bench/right-maximal-quick
```

Smoke used 65,536 reference bases and 12,800 query bases (fingerprint
`2af71e7f80a2963`). Quick used 4,194,304 reference bases and 256,000 query
bases per scenario. Mixed had fingerprint `e03e5f311a2d59c1`; repeat-rich had
fingerprint `f1783ace2d64ab44`.

## Correctness

For every dataset and minimum length, the five internal paths produced the
same total and normalized tuple checksum. The quick mixed workload produced
1,669 candidates at length 20 and 1,666 at lengths 50 and 100. The 40%-template
repeat-rich workload produced 421,210, 421,146, and 421,022 candidates at
lengths 20, 50, and 100.

MUMmer4's MEM output also matched these tuples on the selected datasets. That
is dataset-specific regression evidence, not proof that the current sufkit API
implements MEM semantics: equality on these inputs does not establish the
missing left-maximality contract for all inputs.

MUMmer4 forward output was used for the timed checksum. A separate untimed
reverse-complement gate was run for every dataset/minimum-length pair without
`-c`; its reverse-relative query coordinates were converted to forward
coordinates and matched sufkit's reverse-complement baseline exactly. The
`both` result is consequently validated as the union of the independently
checked orientations.

The library test suite compares all five internal algorithms on deterministic
random multi-contig inputs and covers reference/query N boundaries, save/load,
all auxiliary-section combinations, both strands, result limiting, streaming
callbacks, and exact-search regression. These tests establish internal result
equivalence and the current right-maximal contract; they must not be cited as
two-sided MEM validation.

## Query performance

Median in-process query time in seconds; speedup is relative to the SA-only
baseline for the same dataset and minimum length.

| Dataset | Min | Baseline | LCP | CHILD | Suffix link | Full | Full speedup |
|---|---:|---:|---:|---:|---:|---:|---:|
| mixed | 20 | 0.2100 | 0.2376 | 0.4249 | 0.0579 | 0.0680 | 3.09x |
| mixed | 50 | 0.2047 | 0.2255 | 0.3637 | 0.0724 | 0.1037 | 1.97x |
| mixed | 100 | 0.1673 | 0.1664 | 0.2984 | 0.0903 | 0.1409 | 1.19x |
| repeat-rich | 20 | 2.3903 | 0.5146 | 0.6455 | 0.3555 | 0.3565 | 6.70x |
| repeat-rich | 50 | 1.6992 | 0.4399 | 0.5439 | 0.3098 | 0.3226 | 5.27x |
| repeat-rich | 100 | 0.8541 | 0.3182 | 0.3960 | 0.2412 | 0.2807 | 3.04x |

Suffix-link reuse was the fastest internal mode in every quick case, reaching
6.72x over baseline on repeat-rich/min-20 and 3.63x on mixed/min-20. The full
mode retains the CHILD structure and CHILD traversal, but the current
correctness guard verifies a CHILD-derived branch against character-wise SA
narrowing. That guard makes standalone CHILD slower than baseline and makes
full slower than suffix-link-only. This is a measured limitation rather than a
claimed CHILD speedup; removing the guard is deferred until the compact CHILD
navigation can pass the same randomized differential suite by itself.

MUMmer4 median `-load` plus external-process MEM query time on mixed was 0.3238,
0.3362, and 0.3183 seconds for lengths 20, 50, and 100. These values include
process startup, index loading, parsing, and output, whereas sufkit rows are
in-process query-only measurements. They establish a black-box correctness
and end-to-end reference point, not a like-for-like claim that sufkit is faster
than MUMmer4's query kernel. Because MUMmer4 and the current sufkit API have
different formal contracts, this is also not a general semantic comparison.

## Construction and space

Quick mixed construction and serialized size were:

| Method | Build (s) | Serialized bytes | Bits/base |
|---|---:|---:|---:|
| baseline (SA) | 0.1874 | 20,971,893 | 40.00 |
| LCP | 0.3430 | 37,749,170 | 72.00 |
| CHILD | 0.3774 | 54,526,447 | 104.00 |
| suffix link (ISA+LCP) | 0.3181 | 54,526,447 | 104.00 |
| full (ISA+LCP+CHILD) | 0.3830 | 71,303,724 | 136.00 |
| MUMmer4 saved index | 0.6516 | 37,748,869 | 72.00 |

The full index adds approximately 96 bits/base over the persisted encoded
text+SA baseline. LCP compression is intentionally not part of 0.1.1.

An exact-search quick ablation also compared `sa32-none` (binary search) with
the default full index. Aggregating the generated groups, binary count reached
about 1.04 million queries/s versus 0.33 million for guarded CHILD traversal;
binary locate reached about 0.56 million queries/s versus 0.32 million. Exact
CHILD traversal is therefore correct but not a performance win in this
release.

## Measurement boundaries

- Internal right-maximal exact match wall times are stable medians of five repetitions after a
  warm-up; raw repetitions are retained in TSV.
- The original release runner executed internal methods sequentially in one
  process. Its historical `peak_rss_mb` field can therefore be contaminated by
  an earlier method. Current development runs use isolated workers.
- Current build, save, load, and query RSS values are phase-worker high-water
  marks. The workers are forked after the controller has prepared the current
  reference and queries, so their declared RSS scopes include inherited
  controller dataset pages as well as the phase-specific index work. They are
  not incremental index-allocation measurements.
- The original release output recorded total build/save/load time only.
  Current development output exposes separate ISA/LCP/CHILD/PWL phase timers.
- Current development output measures streaming callback, unbounded vector,
  `max_matches=0`, and `max_matches=1000` separately. It obtains a complete
  count from streaming first and records the unbounded vector row as
  `skipped_high_frequency` when more than 1,000,000 matches would be
  materialized. The streaming and bounded rows still run, and the raw TSV
  records both the threshold and `vector_skipped` flag.
- Quick currently uses 256,000 total query bases rather than a full 1 MiB. This
  keeps the complete repeat-rich result below a practical output/time bound;
  the actual query-base count is recorded in metadata and throughput uses that
  value.
- No large real genome, standard profile, or full profile was run. The
  `--reference`/`--queries` interface is available for user-triggered data.
