# sufkit 0.2.0 low-level performance results

## Scope and decision summary

This report records the implementation and local validation of the low-level
performance work based on:

```text
base branch:  main
base commit:  fd1abbdb4a486abcbca3be7d915f43d3638f8b16
work branch:  codex/v0.2.0-low-level-performance
source state: uncommitted working-tree changes on the base commit
```

The work changes private implementation and developer benchmark code only. It
does not change public C++ headers, public behavior, CLI search commands,
`.sufidx` format/IDs, SDSL templates, sampling rates, or search result sets.
These measurements were collected before the project metadata was updated from
0.1.1. The formally released version containing this work is 0.2.0.

The adopted changes are:

- complete-SA count and `Locate(max_hits=0)` fast paths;
- lazy bounded heaps and direct unbounded result collection;
- non-owning encoded query views and 256-entry normalization/complement LUTs;
- operation-level 32/64-bit dispatch and compact ISA/LCP/CHILD/PWL storage;
- delayed global-coordinate mapping with a monotonic contig cursor;
- a private SSE4.2 compare/LCP kernel and SDSL hardware POPCNT baseline;
- actual-width FM batch SoA workspaces with active-lane compaction;
- streaming FASTA normalization, rolling PWL construction, and fewer
  reference-sized temporaries;
- native little-endian integer block I/O, streaming CRC, heap-backed stream
  buffers, and a measured 1 MiB stream-buffer default; and
- phase-isolated RSS, allocation, suffix-link-scan, and instruction-generation
  evidence tools.

Two deliberate non-adoptions are important:

- CHILD remains available only through explicit algorithms; it is not restored
  to an automatic/default query path.
- A 64-row suffix-link LCP block-min view is not added. In the final
  repeat-rich quick run, scan p95 was 2 rows, maximum was 6 rows, and the
  instrumented scan fraction was at most 6.3%, so neither trigger
  (`p95 >= 64` or repeat-rich scan fraction at least 10%) was reached.

## SSE kernel and POPCNT

The quick kernel covers lengths 1--80, 100, 200, 500, and 4096, critical SIMD
boundaries, mismatch positions, equality, and pointer offsets 0--15. The
complete-matrix metric is the median of seven aggregate repetition ratios. The
remaining rows are medians over all paired case-by-repetition speedup ratios;
an aggregate is naturally weighted toward long/equal inputs.

| Metric | Scalar / production SSE |
|---|---:|
| Complete matrix median speedup | 1.94x |
| Median paired case-repetition speedup | 1.11x |
| Median, lengths <=16 | 1.01x |
| Median, lengths 17--100 | 1.12x |
| Median, lengths >=200 | 1.14x |

SSE is therefore useful for long/repetitive comparisons while the scalar
eight-byte prefix protects early-mismatch DNA. A generic-vs-SSE4.2-only
end-to-end A/B did not show a consistent POPCNT-only win across every FM
backend: stable Huffman count was approximately neutral, while some locate and
balanced rows improved. The larger final gains must not be attributed to
POPCNT alone; instruction evidence and the complete correctness-gated query
results are both retained.

## Exact search throughput

The following ratios are final QPS divided by the original generic baseline
QPS. To reduce microsecond-row noise, only rows whose baseline median was at
least 0.1 ms are included; each cell is the median across matching query
groups, lengths, strands, and applicable limits.

| Method | Mixed count | Mixed locate | Repeat count | Repeat locate |
|---|---:|---:|---:|---:|
| SA32 binary | 2.86x | 2.37x | 2.90x | 2.44x |
| SA32 LCP binary | 3.37x | 3.04x | 4.06x | 3.27x |
| SA32 Sapling | 3.50x | 3.33x | 4.09x | 3.56x |
| FM Huffman | 1.57x | 1.67x | 1.53x | 1.67x |
| FM balanced | 1.56x | 1.60x | 1.59x | 1.69x |
| FM EPR | 1.47x | 1.32x | 1.70x | 1.72x |

The high-frequency `exact_repetitive`, forward, repeat-rich subset makes the
fast-path mechanism easier to see. Values below are medians over pattern
lengths 20, 50, 100, 200, and 500. Unlike the aggregate table above, this
focused table includes all five lengths without applying the 0.1 ms baseline
time filter.

| Method | Count speedup | `Locate(0)` speedup |
|---|---:|---:|
| SA32 binary | 7.45x | 19.87x |
| SA32 LCP binary | 12.29x | 37.17x |
| SA32 Sapling | 7.16x | 27.91x |
| FM Huffman | 1.34x | 448.16x |
| FM balanced | 1.72x | 493.18x |
| FM EPR | 1.59x | 546.66x |

The very large FM `Locate(0)` ratios are expected: the baseline recovered
roughly 64K coordinates only to discard them, while the optimized path computes
the exact interval count and materializes no position. They should not be
generalized to ordinary locate with returned hits.

On the 1,024-contig scenario, stable-row medians were 3.19x/2.55x for SA32
count/locate and 1.69x/1.54x for Huffman count/locate. This result is consistent
with retaining the compact contig arrays and delayed mapping, but the run does
not isolate their contribution from the other low-level changes.

## Sampled suffix arrays

All sampled K=2/4/8 methods agreed with complete SA32/SA64. Under the current
method definitions, sampled binary indexes use `SaAcceleration::kNone`, while
the default complete indexes include SA+ISA+LCP. The size ratios therefore
combine SA sampling with the absence of ISA/LCP; they are not controlled
sampling-only space ratios. The sampled methods did not accelerate exact
queries in this implementation.

| Method (mixed, binary) | Serialized size | Size vs default complete SA+ISA+LCP index | Median QPS vs complete, mixed | Median QPS vs complete, repeat-rich |
|---|---:|---:|---:|---:|
| SA32 K=2 | 12.00 MiB | 23.1% | 0.82x | 0.66x |
| SA32 K=4 | 8.00 MiB | 15.4% | 0.52x | 0.37x |
| SA32 K=8 | 6.00 MiB | 11.5% | 0.30x | 0.22x |
| SA64 K=2 | 20.00 MiB | 23.8% | 0.69x | 0.62x |
| SA64 K=4 | 12.00 MiB | 14.3% | 0.42x | 0.30x |
| SA64 K=8 | 8.00 MiB | 9.5% | 0.27x | 0.21x |

LCP-assisted sampled variants were correct and sometimes modestly faster than
their sampled binary counterpart, but none overtook the complete index. This

## Right-maximal exact-match query

The table compares each current forward algorithm with the current SA-only
right-maximal baseline, using the median over minimum lengths 20, 50, and 100.

| Scenario | LCP | CHILD | Suffix link | Suffix link + Sapling | Full |
|---|---:|---:|---:|---:|---:|
| mixed | 0.86x | 0.30x | 2.93x | 4.56x | 1.26x |
| repeat-rich | 1.90x | 1.20x | 2.42x | 2.69x | 2.26x |
| N islands | 1.03x | 0.35x | 3.49x | 4.52x | 1.68x |
| many contigs | 1.01x | 0.33x | 3.55x | 5.43x | 1.85x |

Relative to the original code (not merely the current baseline algorithm),
forward suffix-link improved by 2.22x on mixed and 1.62x on repeat-rich;
suffix-link+Sapling improved by 2.43x and 1.74x. Reverse-complement and both
were measured separately. Across per-scenario medians over minimum lengths,
reverse-complement suffix-link was 0.96--1.14x the current baseline and
suffix-link+Sapling was 2.32--3.24x. Individual scenario/minimum-length cells
ranged from 0.76--1.30x and 1.49--3.68x, respectively. CHILD remained a
negative optimization on most mixed/N/many-contig paths, so it remains
explicit only.

These throughput ratios come from a library compiled without diagnostic code.
The separate opt-in suffix-link scan pass showed:

```text
repeat-rich p95 rows:       2
repeat-rich maximum rows:   6
repeat-rich fraction range: 3.2%--6.4% depending on method/minimum length
```

The fraction is an instrumented estimate that includes clock-call overhead and
is not used as a release throughput measurement.
The very small scan widths independently show that a block-min structure would
add space and branches without skipping useful 64-row blocks. It was therefore
not implemented.

## FM batch behavior

All scalar, equal-length batch, and mixed-length batch rows agreed. Relative
to the original batch implementation, stable equal-length batch rows improved
by approximately 1.5--1.8x for Huffman/balanced and up to about 2.6x for EPR
on repeat-rich data. Relative to the **current scalar path**, however,
equal-length batching was not universally beneficial:

| Backend | Best equal-length batch/scalar, mixed | Best equal-length batch/scalar, repeat-rich | Best mixed-length batch/scalar, mixed | Best mixed-length batch/scalar, repeat-rich |
|---|---:|---:|---:|---:|
| Huffman | 0.96x | 0.95x | 1.01x | 1.40x |
| Balanced | 1.03x | 1.03x | 1.07x | 1.47x |
| EPR | 0.90x | 0.87x | 1.00x | 1.02x |

The SoA/active-lane implementation is retained because it removes the fixed
256-lane workspace, preserves correctness for mixed lengths, and materially
improves the old batch path. The results do not justify automatically routing
all equal-length scalar queries through batch, nor do they change Huffman as
the default backend.

`batch-mixed` records `query_group=mixed_length` and
`pattern_length=mixed`. This appends no column and is absent unless that method
is requested, but consumers that previously parsed `pattern_length` as an
unconditional integer must account for the documented mixed value.

## Construction time and memory

A separate 64 MiB, sampling-rate-1 benchmark with
`SaAcceleration::kFull` (SA+ISA+LCP+CHILD) used one logical CPU and seven
independent worker repetitions on both the original and final binaries.

| Metric | Original | Final | Change |
|---|---:|---:|---:|
| Build median | 11.658 s | 9.460 s | 18.9% lower (1.23x) |
| Build min--max | 10.351--14.070 s | 8.808--10.158 s | narrower final range |
| Worker peak RSS median | 2436.1 MiB | 1668.1 MiB | 31.5% lower |
| Serialized bytes | 1,140,851,272 | 1,140,851,272 | identical |

Phase-isolated measurements used a 64 MiB, four-contig reference and the
default SA+ISA+LCP layout:

| Method/phase | Original | Final | Change |
|---|---:|---:|---:|
| SA32 index-ready current RSS | 1348.1 MiB | 839.2 MiB | 37.8% lower |
| SA32 build-worker peak | 1925.8 MiB | 1669.0 MiB | 13.3% lower |
| FM Huffman index-ready RSS | 46.1 MiB | 46.7 MiB | approximately unchanged |
| FM Huffman build-worker peak | 559.0 MiB | 495.3 MiB | 11.4% lower |

Query workers retained essentially the index-ready RSS after the fixed query

Rolling PWL construction also removed repeated contig lookup/k-mer rescans.
On the two quick scenarios, the learned-model subphase fell from
0.142--0.155 s to 0.009 s, while the model remained 98,352 bytes and the
serialized index was byte-identical. These are single-build quick observations,
so the byte identity is the stronger release invariant.

## Persistence and stream-buffer selection

CRC is now accumulated while a section is emitted, and integer payloads use a
native little-endian block path when widths match. The final self-validation,
decode-before-trust CRC gate, and bounded SDSL stream remain intact. Temporary
index files are acquired with exclusive creation; `overwrite=false` publishes
with a same-directory atomic no-replace hard link, while explicit overwrite
retains atomic replacement. Stream buffers are heap-backed, avoiding roughly
512 KiB of overlapping stack buffers during save. Exceptional SDSL
construction also removes deterministic text/SA/BWT cache names that may have
been created before SDSL registered them.

The buffer selection benchmark used the same 4 MiB quick reference, 54.5 MB
SA32 index, three save/load repetitions, and CPU 0. The table reports medians:

| Filesystem | Buffer | Save | Load |
|---|---:|---:|---:|
| `/tmp` | 64 KiB | 0.204 s | 0.367 s |
| `/tmp` | 256 KiB | 0.153 s | 0.391 s |
| `/tmp` | 1024 KiB | 0.097 s | 0.140 s |
| `/mnt/d` | 64 KiB | 0.969 s | 1.329 s |
| `/mnt/d` | 256 KiB | 0.677 s | 0.681 s |
| `/mnt/d` | 1024 KiB | 0.536 s | 0.496 s |

Neither smaller buffer was within 98% of the best median in both environments,
so 1024 KiB is the selected default. These are WSL filesystem results, not a
claim about native ext4, XFS, NVMe, or network storage. Buffer sizes were run in
fixed increasing order without dropping filesystem caches. The 1 MiB choice is
therefore an engineering default for this WSL run, not a cache-controlled
filesystem characterization.

The environment did not provide Doxygen, clang-format-18, or clang-tidy-18;
those tools were therefore not used as evidence in this performance task.

## Final interpretation

The strongest adopted improvements are deterministic removal of unnecessary
work, compact 32-bit auxiliary storage, delayed coordinate mapping, the
production SSE comparison kernel, rolling PWL construction, and block/CRC I/O.
They improve both high-frequency queries and construction memory without
changing index bytes or result sets.

Some outcomes are intentionally narrower:

- POPCNT alone was not a universal end-to-end speedup.
- equal-length FM batch is backend/workload dependent;
- sampled SA trades query speed for substantially smaller files;
- CHILD remains useful as an optional capability but is often slower; and
- no claim is made about cache misses, NUMA, native-Linux I/O, standard/full
  profiles, or large real genomes.

Within those boundaries, every correctness gate passed. The combined
implementation met the targeted query-throughput and memory goals on the
reported workloads. POPCNT-only effects, equal-length FM batching, and several
non-isolated implementation changes remain workload-dependent and are not
claimed to meet the 5% threshold independently. No standard/full benchmark,
commit, push, tag, or release was performed.
